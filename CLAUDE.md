# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tile-render-server` renders SVG map tiles from a Planetiler `planet.pmtiles` dataset (Mapbox Vector Tile format). It has two entrypoints that share the same rendering core:

1. **On-demand REST API** (`@fsarch/server`/NestJS) — `GET /v1/tiles/:z/:x/:y.svg`, versioned, with Swagger docs and a health endpoint.
2. **Batch CLI renderer** — walks every tile in a PMTiles archive up to a max zoom and writes `output/{z}/{x}/{y}.svg` using a worker-thread pool.

Requirements are tracked in `REQUIREMENTS.md` (the source of truth for rendering rules, label behavior, and API contracts — consult it before changing rendering logic).

## Commands

```bash
npm run build      # tsc -> dist/
npm start           # fsarch-server start — starts the REST API (reads config.yaml). Requires a reachable, migratable Postgres (see "Database" below).
npm run render       # node dist/cli/index.js — batch CLI renderer (requires build first). No database needed.
npm run example      # node dist/example/example-server.js — static tile viewer, proxies to the API
npm test             # npm run build && vitest run. No database needed.
npm run migration:create --name=<name>  # scaffold a new migration in src/database/migrations/
npm run migration:run                    # run pending migrations against config.yaml's database (dev convenience only — migrations already auto-run on every `npm start`)
```

- Tests live alongside source as `*.spec.ts` (e.g. `src/core/svg.spec.ts`, `src/core/styles.spec.ts`, `src/controllers/tiles/tiles.service.spec.ts`) and run via Vitest (`vitest.config.ts` includes `src/**/*.spec.ts`).
- Run a single test file: `npx vitest run src/core/svg.spec.ts`. Run by name: `npx vitest run -t "places labels"`.
- `npm test` always rebuilds first — the NestJS controllers/services import compiled `.js` paths (ESM, `NodeNext` module resolution), so a stale `dist/` can mask breakage even though Vitest itself runs against `.ts` sources.
- Batch CLI flags: `--input`, `--output`, `--max-zoom`, `--concurrency`, `--overwrite`, `--labels`, `--road-labels`, `--nature-labels` (see `src/cli/index.ts` `parseCli`).

### Database

`npm start` requires Postgres — not for map data (still exclusively `planet.pmtiles`), but as a shared, persistent cache for cross-tile label anchor positions (see Architecture below). `config.yaml` is gitignored; copy `config.example.yaml` and fill in real `database:` credentials. Migrations run automatically at boot (`migrationsRun: true`, hardcoded by the installed `@fsarch/server`); `npm run migration:run`/`src/database/data-source.ts` exist only as a dev convenience for scaffolding/running migrations without booting the whole app. The batch CLI and `npm test` never touch Postgres.

## Architecture

The REST API side of `src/` follows the same layout as the other fsarch `*-server` repos — `main.ts`/`app.module.ts`/`controllers/`/`repositories/`/`database/` flat under `src/`, no extra wrapper folder — with the map-rendering-specific pieces (shared pipeline, batch CLI, dev viewer) sitting alongside as their own top-level folders, since a pure API repo has no equivalent for those:

```
src/core/         → rendering pipeline shared by both entrypoints (pmtiles, renderer, geometry, styles, svg, label-anchor-cache)
src/cli/          → batch CLI entrypoint (index.ts driver + worker.ts worker-thread body)
src/controllers/  → REST API controllers, one folder per resource (fsarch convention)
src/repositories/ → TypeORM-repository-backed services, one folder per entity (fsarch convention)
src/database/     → entities/, migrations/, index.ts (fsarch convention)
src/storage/      → IStorageProvider (filesystem/S3) backing storage.data/storage.cache (mirrors michael-braun/image-server's storage module)
src/main.ts, src/app.module.ts → REST API bootstrap (fsarch convention)
src/example/      → static tile-viewer dev server + its static assets (public/)
```

Both entrypoints funnel through the same `src/core/` pipeline, kept in strict separation of concerns:

```
pmtiles.ts   → open a PMTiles archive, fetch raw tile bytes, enumerate tile coords
renderer.ts  → decode MVT, apply per-feature rendering/label rules, orchestrate layer order
geometry.ts  → decode+normalize MVT geometry (extent -> 256px), area/length helpers, label anchors
styles.ts    → pure lookup tables: layer order, per-feature style, text style, CSS class names
svg.ts       → pure string builders: turn geometry/style into SVG path/circle/text markup
```

- **`src/core/pmtiles.ts`** wraps the `pmtiles` package with a Node `fs`-backed `Source` (`NodeFileSource`) so archives can be read from local disk without HTTP. `LocalPMTilesArchive` exposes `getTile(z,x,y)`, `countTiles`, and an async generator `iterateTileCoords` (walks the PMTiles directory tree recursively via `iterateRunEntries`).
- **`src/core/renderer.ts`** (`renderTileToSvg`) is the core: decodes the MVT buffer, iterates `getLayerOrder()` from `styles.ts`, and for each layer renders geometry + optional labels. Label logic is the most complex part — separate code paths exist for generic feature labels, road labels (`renderRoadLabels`, priority-filtered by zoom/road class), and nature/water labels (`renderNatureLabels`, with cross-tile dedup bucketing via `buildGlobalLabelBucketKey` and overlap-based candidate selection via `pushBestNatureLabels`). All labels render in an overlay group *after* geometry layers, in the fixed order: road labels → feature labels → nature labels.
  - **Cross-tile area-label resolution**: large named `park`-layer features (nature reserves, forests) get clipped by Planetiler/MVT tiling into many disjoint per-tile fragments. `computeAreaGlobalAnchor` walks to coarser ancestor-zoom tiles (or falls back to a bounded neighbor scan) to find one canonical world position for the whole feature; only the tile that geographically owns that position renders the label (`resolveOwnedLocalAnchor`), others suppress their local fragment. Matching is **by the feature's MVT/OSM id** (`getFeatureDataId`), not name — several genuinely distinct real-world features can share one name (see REQUIREMENTS.md §9's "Borkenberge" example), so grouping by id avoids merging them into one wrong combined position; a per-tile scan still falls back to name-matching for one hop during the ancestor walk (ids reliably survive tile-clipping within one zoom level but aren't guaranteed to survive Planetiler's cross-zoom generalization), and features with no id at all fall back to name-matching entirely via a synthetic `name:<normalized>` key. Resolved anchors are cached through the injectable `LabelAnchorCache` (`src/core/label-anchor-cache.ts`) — `InMemoryLabelAnchorCache` (default, used by the batch CLI/tests) or `PostgresLabelAnchorCache` (`src/repositories/label-anchor/label-anchor-cache.postgres.ts`, wired in by `LabelAnchorModule`, `RepositoriesModule` and injected into `TilesService`), a shared, persistent store so resolution survives process restarts and is reused across multiple API instances.
  - **Cross-tile line-label continuation** (roads/rivers, see REQUIREMENTS.md §9): `extendLineAcrossTileEdges` handles the separate case of a road/river name whose line touches a tile edge — rather than the area-anchor cache above, this is a cheap single-hop join computed fresh per request, never persisted. `lineEdgeDirectionsTouched` finds which edge(s) the local line touches, `findMatchingLineInTile` locates the same feature (by id, or by name when the feature has no real id) in the same-zoom neighbor tile across that edge, and `joinLines` stitches the two lines end-to-end (translated into local tile space, so the joined line legitimately extends past `0..256`). Both tiles sharing the boundary independently build the same combined line offset into their own space; rendering each tile's `<textPath>` against its own copy and letting the SVG viewport clip to `0..256` is what makes the text split naturally across the boundary (upper half in the tile above, lower half below), instead of being suppressed or duplicated. Because each tile is now expected to show only *part* of the text, `buildLineLabelBounds`'s usual ~90%-visibility truncation guard is relaxed (`requireHighVisibility = false`) whenever a line was actually extended.
- **`src/core/geometry.ts`** normalizes raw MVT coordinates (typically 0–4096 extent) into the fixed 256×256 tile space, and provides `getLabelAnchor` (point centroid / line midpoint / polygon centroid of the largest ring).
- **`src/core/styles.ts`** is data-driven and side-effect-free: `LAYER_ORDER` defines the canonical `land -> landuse -> water -> boundaries -> railways -> roads -> buildings -> places -> labels` order; per-layer source-layer name mappings, style tables, and zoom/importance-based text style rules (e.g. suppressing small `village`/`town` place labels below zoom 9) live here. Changing what's visually distinguishable (colors, widths, label thresholds) belongs in this file, not in `renderer.ts`.
  - **Themeable colors** (REQUIREMENTS.md §18): rendering and styling are deliberately separate, so a rendered tile can be cached independently of its color theme. Every color a `Template` may override (`THEMEABLE_COLOR_VARIABLES`: background, water, buildings (fill *and* stroke share one variable), roads grouped by the same priority classes REQUIREMENTS.md §8.2 already singles out (motorway/trunk/primary/secondary/tertiary, everything else sharing `--road-minor`), railways, label text/halo colors, and landuse ground cover grouped by broad category — `--map-landuse` for "green" nature (forest/park/meadow/grass/scrub/heath/shrub/wetland, i.e. what a user would call "Naturflächen"), `--map-urban` for residential/commercial/industrial/railway zones, `--map-farmland` for farmland — is emitted via the `themedColor(variable, fallback)` helper as `var(--the-name, <today's-hardcoded-value>)`, never a bare hex value. This is a curated, not exhaustive, list; rarer/niche variants (bare ground, sand, rock, ice/glacier) and the nature-reserve label color override in `renderer.ts` stay hardcoded. **Important subtlety**: several variables intentionally bundle multiple originally-distinct shades under one name (documented per-variable in `src/database/seeds/default-template.sql`) — a tile renders pixel-identical to before this existed only when **no template is active at all**; the seeded "default" template itself only sets the subset of variables that map 1:1 to a single color (e.g. `--road-motorway`), deliberately omitting every bundling variable so it doesn't flatten those groups.
- **`src/core/svg.ts`** has no domain knowledge — it only turns already-decided geometry/style/class/attributes into SVG markup strings (`<path>`, `<circle>`, `<text>`/`<textPath>`), plus railway sleeper-tick rendering and final document assembly (`buildSvgDocument`, which groups content by `<g id="...">` per layer and appends the label overlay last). `injectStyleTemplate(svgDocument, colors)` is the one place a template's colors ever touch a document: it filters `colors` down to `THEMEABLE_COLOR_VARIABLES` and to values that look like a plausible CSS color (unknown keys/implausible values are dropped rather than failing the request) and inserts a `<style>:root{...}</style>` block right after the opening `<svg>` tag — called by `TilesService` as the very last step before responding, never by `renderTileToSvg` itself.
- **`src/cli/worker.ts`** is the `worker_threads` entrypoint used by the batch CLI (`src/cli/index.ts`): each worker owns its own PMTiles archive handle and renders tiles pushed to it via `postMessage`, skipping existing files unless `--overwrite` is set.
- **`src/cli/index.ts`** is the batch CLI driver: opens the archive once to compute `totalTiles`, spins up a worker pool sized by `--concurrency`, streams `iterateTileCoords`, and prints periodic progress/ETA.
- **REST API** (`src/main.ts`, `src/app.module.ts`, `src/controllers/**`): built on `@fsarch/server`'s `FsArchAppBuilder` wrapping NestJS. `TilesController` (`v1/tiles/:z/:x/:y.svg`, in `src/controllers/tiles/`) validates coordinates (regex + bounds check against `2^z - 1`) before calling `TilesService.renderTileSvg`, which lazily opens a single shared PMTiles archive (`onModuleInit`/`onModuleDestroy` lifecycle, path resolved from the active `DatasetVersion` row — see below) and calls the same `renderTileToSvg` used by the batch path, passing its injected `PostgresLabelAnchorCache`, then injects the active `Template`'s colors (`injectStyleTemplate`) as the last step before returning. `TemplatesController` (`v1/templates/:id/tiles/:z/:x/:y.svg`) is the same rendering path with an explicitly-chosen template instead of the active one — see below. All controllers' routes use `@Public()` from `@fsarch/server/auth`. Runtime config (label toggles, cache-control header, Postgres credentials, `tiles.maxZoom`) comes from `config.yaml` via `@nestjs/config` — note there is no `tiles.input` anymore; the pmtiles path is DB-only (see below). `main.ts` wires the database via `.setDatabase(DATABASE_OPTIONS)` and listens on `process.env.PORT` (fsarch convention: no host binding, no config-file port — just `app.listen(process.env.PORT ?? 3000)`, matching the other fsarch `*-server` repos).
  - **Dataset versions and templates** (REQUIREMENTS.md §18): the `dataset_versions` table (one `path` to a pmtiles file per row, at most one `is_active` at a time — enforced by a partial unique index) replaced `tiles.input` entirely; `TilesService.getInputPath` reads the active row via `DatasetVersionService.getActive()` once, at archive-open time — like the old config setting, a newly-activated row only takes effect on the API's next restart (the opened archive isn't hot-swapped). `path` is a *key* resolved through `storage.data` (see below), not necessarily a literal filesystem path. The `templates` table (`name` + `colors` jsonb + `is_active`, same single-active-row constraint) supplies the color theme `injectStyleTemplate` applies: `GET /v1/tiles/:z/:x/:y.svg` (`TilesController`) uses whichever one is `isActive` (`TemplateService.getActive()`), while `GET /v1/templates/:id/tiles/:z/:x/:y.svg` (`TemplatesController`, a thin wrapper that just forwards to the same `TilesService.renderTileSvg`, now given a `templateId`) picks one explicitly by id (`TemplateService.getById()`) regardless of which is active — a 404 if that id doesn't exist. Both are looked up fresh on *every* request, so switching templates (by activating a different one, or just requesting a different id) takes effect immediately, no restart, since it never touches the opened archive or re-renders anything. There is currently no admin API for creating/activating rows in either table; they're managed by direct SQL (see README.md "Datasets und Themes"). The persisted cross-tile label-anchor cache (`label_anchors.dataset_version`, see below) is scoped by this table's `id` via a real foreign key (`ON DELETE CASCADE`) — `TilesService.getInputPath` calls `PostgresLabelAnchorCache.setDatasetVersionId(activeVersion.id)` as soon as it resolves the active row, before any tile is rendered; there is no separate `tiles.datasetVersion` config string anymore.
  - `src/controllers/tiles/tile-request.util.ts` holds the HTTP-layer bits shared by both controllers (`parseTileCoordinate`, `assertTileBounds`, `writeSvgResponse`) — both routes validate/render/respond identically, only *which* template they resolve differs, so that part lives once instead of being duplicated per controller.
  - **Storage and the rendered-tile cache** (REQUIREMENTS.md §19; `src/storage/`, mirroring michael-braun/image-server's storage module for consistency across projects): `IStorageProvider` (`readFile`/`writeFile`/`readRange`/`exists`/`mkdir`/`deleteFile`) is implemented by `FileSystemStorageProvider` (paths relative to a configured base directory), `S3StorageProvider` (`@aws-sdk/client-s3`, keys relative to a configured bucket/prefix), `MemoryStorageProvider` (an in-process `Map`-based LRU, bounded by `maxItems`/`maxBytes`), `LayeredStorageProvider` (wraps an ordered list of other providers — reads check each in turn and return the first hit, promoting it into every faster/earlier layer; writes/deletes/`exists` fan out to/across all of them), and `ZoomRestrictedStorageProvider` (wraps one other provider, gating every call on `extractZoomFromCacheKey(path)` falling within a configured `minZoom`/`maxZoom` — out-of-range treats the path as absent: `exists()` false, `mkdir`/`writeFile`/`deleteFile` silent no-ops, `readFile`/`readRange` throw; a path whose zoom can't be parsed at all is never restricted, fail-open rather than silently dropping unanticipated data). `storage.data` (`StorageProviderFactory.create`, a `StorageConfig`: bare string, or `{ type: "filesystem" | "s3", config: {...} }`) is always a single filesystem-or-S3 backend — no memory layer, no zoom restriction, since a multi-GB pmtiles archive doesn't benefit from either the way small rendered tiles do. `storage.cache` (`StorageProviderFactory.createCache`, a `CacheStorageConfig` — everything `StorageConfig` allows, plus `{ type: "memory", config: {...} }`, plus an optional `minZoom`/`maxZoom` on any single layer, plus arrays of itself for layering) is where memory-first and zoom-scoped caching are actually configured: `[{ type: "memory" }, { type: "s3", maxZoom: 14, config: {...} }]` means "look in the memory cache first (any zoom), and if it's not there, check S3 — but only for zoom ≤ 14" (e.g. so overzoomed tiles never fill up an S3 cache bucket). `StorageModule` builds both from `config.yaml` and provides them as `DATA_STORAGE_PROVIDER`/`CACHE_STORAGE_PROVIDER` (not `@Global()`, unlike image-server's — only `TilesModule` needs them). `readRange` exists specifically because PMTiles archives (hundreds of MB to several GB) are never read in full — `src/core/pmtiles.ts`'s `StorageSource` (a `pmtiles` package `Source` implementation) and `openPMTilesArchiveFromStorage` back `storage.data` reads with it, alongside the pre-existing `NodeFileSource`/`openPMTilesArchive` (unchanged, local-filesystem-only, still what the batch CLI uses — storage.* is REST-API-only). `TilesService.renderOrGetCached` checks/writes `storage.cache` at key `${datasetVersionId}/{z}/{x}/{y}.svg` *before* template injection — the cache holds the same var()-referencing, un-styled render `injectStyleTemplate` always starts from, so one cached tile serves every template (and every cache layer), and switching templates never invalidates it. Scoping the key by `datasetVersionId` (not just z/x/y) is what keeps a `dataset_versions` swap from ever serving another dataset's stale cached tile.
  - **Overzoom** (REQUIREMENTS.md §17, API only — the batch CLI never overzooms): when a request's `z` exceeds the dataset's own `header.maxZoom`, `TilesService` fetches the deepest real ancestor tile instead (`computeOverzoomTransform` in `geometry.ts` maps the request to that ancestor's `(z,x,y)`) and passes the *original* request plus `datasetMaxZoom` through `RenderOptions` so `renderer.ts` knows to crop+scale. Disabled by default (still 404s above `header.maxZoom`, exactly as before); enabled by setting `tiles.maxZoom` above the dataset's real max zoom, which raises the serving ceiling without ever lowering it. `renderer.ts` applies the same transform everywhere it decodes geometry for the request — the main tile's own layers *and* any neighbor/ancestor tile fetched for cross-tile line-joining or area-anchor resolution (`safeGetVectorTile` returns the transform alongside the decoded tile) — so those mechanisms stay correct under overzoom without any special-casing; zoom-dependent styling/label-visibility rules still key off the requested (overzoomed) `zoom`, never the dataset's real max zoom — except `shouldRenderRoadLabelByZoom`'s "high-priority roads only" clutter guard (REQUIREMENTS.md §8.2), which is calibrated for the dataset's own real detail and is explicitly lifted once `zoom` exceeds `datasetMaxZoom` (a tile then covers a much smaller area, so there's room to label every road class again).
- **`src/repositories/`** (fsarch convention: TypeORM-repository-backed services, kept separate from `controllers/` even when a controller is their only consumer) holds one folder per entity — `label-anchor/` (`PostgresLabelAnchorCache`), `dataset-version/` (`DatasetVersionService`: `getActive`/`list`/`create`/`activate`, the latter transactionally deactivating every other row first), `template/` (`TemplateService`, same shape) — each with its own `*.module.ts`, aggregated by `repositories.module.ts` and imported by `app.module.ts`; `TilesModule` imports all three directly to inject their services into `TilesService`.
- **`src/database/`**: `entities/label-anchor.entity.ts` (the `label_anchors` cache table, composite natural PK — see cross-tile resolution above), `entities/dataset-version.entity.ts` and `entities/template.entity.ts` (both `uuid` PKs generated app-side via `crypto.randomUUID()` in their service, not a DB default — matching the fsarch convention and avoiding a Postgres UUID-extension dependency), `migrations/`, `index.ts` (exports `DATABASE_OPTIONS` consumed by `main.ts`), `data-source.ts` (CLI-only `DataSource` for the `migration:*` npm scripts, not imported by the app itself).
- **`src/example/example-server.ts`** + **`src/example/public/`** (`index.html`, `app.js`, `style.css`) is a minimal static Leaflet-style viewer that fetches tiles from the REST API (`--api-base` overridable) and persists zoom/position in the URL hash. `public/` isn't compiled by `tsc` (only `src/**/*.ts` is); `example-server.ts` resolves it from the project root at runtime (`<root>/src/example/public`) regardless of whether it's running as source or as compiled `dist/example/example-server.js`, so the assets don't need a separate copy-to-`dist` step.

## Conventions

- ESM throughout (`"type": "module"` in `package.json`, `NodeNext` resolution) — internal imports use explicit `.js` extensions even in `.ts` source files.
- Keep `styles.ts`/`svg.ts` free of cross-concern logic: styling decisions (what/how something looks, zoom thresholds, suppression rules) belong in `styles.ts`; markup generation belongs in `svg.ts`; feature-selection/orchestration logic belongs in `renderer.ts`.
- `REQUIREMENTS.md` encodes specific, testable rendering rules (e.g. exact zoom thresholds for suppressing labels, which road classes get labels at zoom 13+, `naturschutzgebiet` styling). When changing label or styling behavior, check it for a rule you might be breaking, and update it if a requirement changes.
